Agentix serving 的 process 层次分析与 trace —— 面向进一步优化

目的：为后续性能优化（动态并发/抢占机制探索，S1–S4 计划）提供分析基座。 对象：agentix_core 臂（论文机制本体）。版本注：本页为 v0 草稿——基于 r0.5 开环采集；正式版将换用受控并发 batch 采集（batch8/16 方法：构造并发相位凸显机制特征，计划见 workflow06/B_BATCH_TRACE_PLAN.md）。process 宇宙分层沿 auto_trace batch8/16 契约（request→forward/iter→scope→kernel，10 % 阈值 + 对数时长五堆聚类 + 全局排名）。四臂消融与机制学习在姊妹文档《R10_ABLATION》。

B1 负载场景、process 层次与方法（合并简述）

场景先行。本负载取三个真实 agent 场景：工具代理（bfcl——模型 反复调用外部工具，每次生成短，调用之间隔着工具延迟）；多轮会话（sharegpt——人与模型 往返，每轮生成长）；树搜索（lats——MCTS 式搜索，每波 5 路并行展开、近两百次生成连成 深链）。论文图 1 给出这类场景的一般形态（DAG）：

由场景到定义。要说清这三种场景在 serving 引擎里的行为，需要四层 词汇：一个场景实例（会话/任务全程）称为 program（三类共 25 个）；program 内的一次 LLM 请求是 call（共 2,440 个）；引擎的一次连续批迭代是 step（一个 step 同时 服务至多 16 个 call 各一次 decode 迭代，约 1.5 万步/捕获）——一个 call 的服务由几十到上千个 step 拼成，这就是"调度只能改 call 进 step 的顺序、改不了 step 本身"的结构原因；step 内的 引擎阶段是 scope（schedule / prepare / forward / sample 等，B2 的 DFG 画的就是 它们）。三类场景的区分完全落在前两层：bfcl = call 短而多，sharegpt = call 长而少， lats = call 洪流 + 波并行：

B1b 负载场景的生命周期 —— 用四层定义串起来

把定义放回场景（下面三张图是各类一个中位规模的真实实例，opt 臂 trace）： bfcl program 的生命周期是"call（等待→服务）→ 工具延迟 → 下一 call"的串行链，寿命由等待与 工具延迟主导；sharegpt program 是少数长 call 的接力，寿命由服务段主导；lats program 是每波 5 个并行 call 的推进，波内要等最慢一路（关键路径）——它的 call 都小，program 却最长。

一句话看图：红多彩少、段间有空隙——寿命被等待与工具延迟主导。bfcl 的生命周期：串行工具链：调用短而密，寿命被『等待+工具延迟』主导。红段 = 等待（提交→首token），彩段 = 服务；横轴为该程序自身的寿命时间。

一句话看图：彩段远长于红段——寿命被长 decode 服务主导。sharegpt 的生命周期：会话链：调用少、decode 长（彩段远长于 bfcl），寿命被服务段主导。红段 = 等待（提交→首token），彩段 = 服务；横轴为该程序自身的寿命时间。

一句话看图：五行并行波逐波推进——每波等最慢一路，寿命=关键路径。lats 的生命周期：树搜索：5 路并行波推进，寿命 = 关键路径（最慢的一路决定下一波开始）。红段 = 等待（提交→首token），彩段 = 服务；横轴为该程序自身的寿命时间。

方法回顾（一段话）：Agentix 用全局进程表记每程序累计服务 {Tp, Wp}，call 到达时按 p(cj) 离散化准入 Q0–Q3、 time quantum 用尽降级、β 抗饿；本采集中该状态机的账本：准入 97/102/237/2004、降级 151 次。 架构与状态机原图：

两个可优化的高延迟来源（数字）：① async 输出等待：GPU 已出 token、 host 未消费的跨步空档，core 臂 109 s / 均 8 ms 级——超过 forward 本身； ② quantum 续段的再 prefill：被切 call 的后续 quantum 段要重算已生成上下文（core 臂 161 个续段，首段中位 2,587 ms 对续段 977 ms）——机制自身的 执行代价。
