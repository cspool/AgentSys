# 机制复现 → 性能实验 → workload_analysis → perf_trace 完整工作流（M0–M4）

适用场景：论文提出一个**可作为单开关接入的系统机制**（调度、缓存、批处理策略等），要求
(1) 复现其机制，(2) 用论文口径复现其性能提升，(3) 用 AutoTrace 两半链解释提升从何而来。

来源实践：h23（Agentix / Autellix NSDI'26，LLaMA-3.1-8B + Qwen3-1.7B + Qwen2.5-VL-3B，
单卡 RTX 4090，github.com/cspool/AgentSys）。本文件记录踩过的坑与其判据，避免重犯。

## 阶段总览

```
M0 机制复现      → 机制在 trace 内可自证（账本），且端侧可测
M1 性能实验      → 论文口径的加速比/提升比（不是随手一个口径！）
M2 工况定点      → 由 M1 的曲线选定"收益存在"的工作点
M3 workload_analysis (W1–W5) → 代表 process 集 + perf_trace 覆盖判定
M4 perf_trace (A00–A05)      → 三类时间线解释收益
```

强制顺序：**M1 必须早于 M3/M4**。若先 trace 后测性能，很可能 trace 在一个没有收益的工作点上，
三类时间线只能解释"为何无收益"（h23 第一次就是这样，r0.1–0.8 非排队制下三策略无差异）。

## M0 机制复现

1. **确定论文实际评估的 baseline 臂**，不是泛指的前作。h23：vLLM、vLLM-opt（前缀缓存 +
   chunked prefill 的 FCFS）、朴素 MLFQ。本机 vLLM 0.29 默认已开前缀缓存与 chunked prefill，
   故 `--policy fcfs` 臂 ≈ 论文的 vLLM-opt。
2. **区分"接入项"与"要自己实现的创新点"**：引擎原生已有的（优先级调度、前缀缓存、KV offload）
   只需接入；论文的性能优化机制必须自己实现。h23 的教训：第一版只把静态优先级传给
   `scheduling_policy="priority"`，那是"程序级优先级排序"的下界，不是论文的 MLFQ。
3. **论文未给的常数自行标定并声明**。h23：K=4、入队界 [0,2,8,32] s、量子 32/64/128/256 token、
   β=2.0，全部写进报告与 protocol。
4. **机制必须在 trace 内自证**：把机制事件做成一等 process（量子块 chunk_begin/end、降级、
   提升），而不是只在日志里留字段。h23 实测账本：2,601 量子块 / 151 降级 / 0 次 β 提升。

**验收**：账本数字与机制语义自洽（如降级次数 ≤ 多量子调用数）；关掉机制后账本归零。

## M1 性能实验（论文口径）

### 口径陷阱（h23 犯过）

论文 Fig.12 那类 "2× / 5×" 通常是**吞吐口径**：在同一延迟水平线下，两条 latency-vs-arrival-rate
曲线能承受的到达率之比（膝点右移）。而"固定到达率下的延迟比"是另一个量。排队系统里两者
不可互换——膝点前曲线平坦，延迟比会显著低估机制收益。

h23 错误示范：用 0.5 prog/s 下的 ptl 比值 1.35× 去对论文的 2×，声称"误差 −10 %"。作废。

### 正确做法

1. **先造出排队**。机制若只在排队制生效（程序级调度就是），必须用统一 max-batch 上限等手段
   制造排队，并确认这符合论文协议（Agentix §6.2 允许同 batch 上限对比）。
   判据：above-cap 累计时长 > 0 且两臂相近。
2. **扫到达率**，两臂同负载同种子，≥5 个点，覆盖膝点两侧。h23：0.2 / 0.35 / 0.5 / 0.8 / 1.2 prog/s。
3. **两个口径都报**：
   - 吞吐口径（对齐论文）：固定延迟阈值下的到达率之比；
   - 延迟口径（补充）：各到达率下的 mean/p90/p99 比值。
4. **报吞吐饱和平台**：若机制只重排等待、不改服务时间，两臂的饱和吞吐应接近；平台差异说明
   机制引入了额外开销（h23：客户端 continuation 重提交使重 forward 堆多 2.3 s）。

**验收**：曲线覆盖膝点；两口径都给出；与论文数值的差距有归因（硬件、负载轨迹、抢占能力）。

## M2 工况定点

从 M1 曲线选一个**收益确实存在**的工作点做后续 trace。选点准则写进审计文件：
通常取"机制与 baseline 的延迟曲线开始分离、但两者都未完全饱和"的那个到达率。

**验收**：该点上机制对 baseline 的提升可测且显著；该点的 above-cap 时长记录在案。

## M3 workload_analysis（W1–W5，每模型串行，一步一卡）

见 `06_ablation_paired_trace_three_timeline_explanation.md` 的 A0W 节。要点复述：

- **W1 试运行**：短定长 + CPU 采样（`--sample=process-tree` + osrt + 上下文切换）。
- **W2 热点定位**：UNION 时间排名；头号 host process 的 CUDA-API vs 纯 host 拆分（**按引擎线程
  过滤**，跨线程 OSRT 不可归因）；容器内部归因率；**空闲边界榜 = 命名区间并集在 step 内的补集**
  （逐对相邻区间算 gap 会在嵌套长区间上造假空隙，h23 曾得 99,457 s）。
- **W3 插桩修订**：按 W2 增删探针，去重复项，机制事件升为一等 process，**复测插桩开销**
  （h23：−0.9 %，故时间线可与旧捕获对比）。
- **W4 代表性采集**：完整负载 + 修订插桩，关 CPU 采样（避免扰动）。
- **W5 代表集选择**：host 分母 = UNION(step) − UNION(forward)；贪心选叶至覆盖目标；
  输出容器归因、空闲边界、**perf_trace 覆盖差**与 COVERED / RECAPTURE_REQUIRED 判定。

**验收**：三模型各出代表集；判定 RECAPTURE_REQUIRED 时 M4 必须带修订插桩重采。

## M4 perf_trace（A00–A05）

见同一文件的 A00–A05 节。要点复述：

- **A00** 守恒门：program / call / step / scope 四层，G-P / G-C / G-S / G-J 四门全过才放行。
- **A01** 单变量配对采集（唯一变量是机制开关）。
- **A02** workflow05 契约双页（>10 % 选型、5 堆对数时长聚类、梯形、折叠十段）。
- **A03** 配对事实（端侧比值、分类别等待、队深、机制账本、堆差量）。
- **A04** 三类时间线（端到端无损车道 / 高延迟分堆 / 并发资源 lanes），每类共轴成对。
- **A05** 总结文档：预备节（字符画 + 生命周期图 + 组成表）→ 三部分（论文方法卡 → 示意图 →
  实现卡 → 读图卡 → trace 图 → 解释）；选材标准入审计文件；排版与几何按
  `skills/ablation-timeline-reporting/references/report-template.md`。

**验收**：A00 全过；三类视图共轴同窗；时间线重放上界与 M1 实测口径一致（见下）。

## 闭环校验：M1 与 M4 必须互证

这是整条链的收敛判据，也是它值得走一遍的理由：

| 来源 | 量 | 应满足 |
|---|---|---|
| M4 高延迟 step 堆 | 两臂重 forward 堆同形 | 服务时间不变 ⇒ 收益纯来自排序 |
| M4 时间线重放 | 上界估算（等待段替换法） | M1 实测 ≤ 上界 |
| M1 曲线 | 饱和吞吐平台 | 两臂接近（差值 = 机制自身开销） |
| M4 并发 lanes | busy / gemm / 在飞 | 两臂同形 ⇒ 资源与并发不是自由度 |

任一条不满足，说明前提（服务时间不变）或估算模型有问题，回 M4 的 step 堆重查，而不是
调整结论。
