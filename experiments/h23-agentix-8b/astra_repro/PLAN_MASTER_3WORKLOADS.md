# 计划 1:agent 优化方法对照——程序级调度(baseline)vs workload+trace 归因(我方)

更新:2026-09-21(全文重写梳理;旧版按时序追加的段落已并入各节)

## 0. 方法核心(规范表述)

**找到端到端过程中的优化机会,机会分三类:资源墙、并发墙、高延迟。**
**优势:每个机会都能直接定位到代码区间(插桩区间)和 process 类型。**
(完整定义见 perf_trace_v3/references/method-spine.md;四层对象
prog/step/process/kernel,三遍漏斗 P1 NVTX-only → P2 条件触发 → P3 条件门控。)


## 方法管线(规范,2026-09-21——profile+trace 串行,多轮迭代)

每轮迭代 = 两段串行 + 决策:

1. **profile(process→FX graph 定义)**:对目标引擎/模型做 FX graph 捕获 →
   算子级闭包划分 process(unclaimed 节点=0 为闸门)→ 生成 NVTX 插桩点。
   process=代码区间的"定位性"由本段构造保证;**新引擎/新模型架构接入必须
   先跑本段**(不允许跳过 process 定义直接 trace;确不可行处逐架构声明);
2. **trace v3(三遍→perf timeline)**:P1 NVTX-only 整段 → P2 条件触发窗口 →
   P3 条件门控计数器,串行、独立验收,产出四层 perf timeline(prog/step/
   process/kernel);
3. **优化决策**:三类机会(资源墙/并发墙/高延迟)→ 发现→杠杆映射 →
   实施 → 兑现率审计;
4. **多轮迭代**:每次修复后系统已变,旧归因过期——**必须回到 ① 重新
   profile+trace**(实测教训:eager 臂归因外推到图臂两次失败);判停 =
   最高层发现余量 < 噪声带。

本方法 ≠ 仅 trace:profile 段是定位性的来源,trace 段是证据的来源,
迭代是有效性的来源,三者缺一即退化为一次性归因。

## 1. 目标(2026-09-21 校准:自动优化 vs 自动优化)

在**多 agent 场景负载**上对照两个**自动优化器**,严格同条件:
同 serving 栈、同负载、**同杠杆库**(策略/图模式/kv dtype/…,全为现成机制,
双方共享)、**同实验预算**、同评分(性能+内容漂移门+代价账本)、同 LLM
(声明替换,决策链落盘)。唯一差异 = 感知与决策方法:
- baseline 优化器:黑盒反馈循环(墙钟/延迟摘要 → 猜下一配置,Astra/PRAGMA 式);
- 我方优化器:归因循环(每轮 P1 四层归因 → 发现→杠杆映射 → 兑现率审计→判停)。
判据:预算内最优配置、到达轮数、错误归因次数。
预注册:黑盒方在大杠杆库下按墙钟梯度盲搜,预算耗于无信息臂;
归因方首轮即指向发射路径,并能在兑现率审计下自我否决坏杠杆。

## 4. 实验设计与当前结果

### 4.1 调度阶梯——已完成(定位校准:机制族天花板的子问题,非主对照)
四策略在 pt_agentloop2 上统计不可分(tok/s 251.8–255.3,makespan p50
64.8–65.7s,<1.4%):深串行链、低队列竞争场景,调度没有可重排对象。

### 4.2 我方归因臂——进行中(同批重跑含内容哈希)

**归功声明**:各臂杠杆(cudagraph/FP8 KV/MPS)均为 vLLM/NVIDIA 现有机制,
不是我方贡献;我方方法 = 归因与决策层(定位哪层有钱 → 选现有杠杆 →
兑现率审计与否决)。对照是"两种选杠杆的方法"之争,杠杆归生态。
本系列唯一自造机制:DAG 执行语义修复(prog 层归因独有发现,−37% makespan)。
- 轮 1:P1 步内空隙 → 图捕获(piecewise):+2.7%,为调度阶梯散布的 5–7 倍;
- 轮 2:process 表 attn_core 54.5% × DRAM 墙推 FP8 KV → +1.3%,兑现率审计
  揪出 host/device lane 混淆(54.5% 为 host 派发,own 设备重叠仅 10%)——
  已入目录(lane 混淆为本方法头号天敌);
- 轮 3:FULL_DECODE_ONLY 反而 −1.3%(混合批回落 eager;且 eager 臂的归因
  不能外推到图臂)——**循环纪律:每修一轮必须对新系统重新 P1**;
- 下一轮:对图臂做 P1,定位其剩余墙(预期:调度器/准备段 host、串行链结构、
  工具延迟窗)。

## 5. 执行约束(强制)

1. **严格按 profile+trace 定义串行执行**:三遍四层按步串行,每步独立验收;
   不得跳步/并行化 GPU 步/以临时脚本绕过链驱动。
2. **修改即升版**:profile/trace 定义的任何修改 → v3→v3.1→…,新 manifest/
   skill/runtime/指纹;禁止旧谱系原地改语义。
3. **复用三条件**(合同 §0):同输入+已验收+指纹一致,缺一即重跑;撤回产出
   入 _stale 不可读。版本/指纹/决策入账本。

## 6. 对照协议(强制——臂间唯一差异=内部优化)

固定项(逐字节一致,记 sha):负载 json+sha、seed、model-dir、引擎与服务启动
参数(policy/max-num-seqs/max-model-len/gpu-mem-util/device/dtype/
prefix-cache/chunked-prefill)、harness sha(serve_agentix/astra_swap,同批同版)、
容器镜像/driver/CUDA/LD_LIBRARY_PATH/VLLM_* 环境、GPU 型号、评分脚本。
唯一变量:被测优化开关,逐臂枚举。
登记义务:每臂目录必须含 launch_manifest.json(argv/参数/各 sha/env/GPU/时间戳),
缺 manifest 不得进对照表(astra_swap 已自动落)。

## 7. 优化代价与公平条款(强制)

任何机制(SPD/量化/KV 复用/图捕获/…)可按分析结果尝试,但每臂带代价账本:
{机制,内容级精度证据(token-id 哈希;禁止用被 ignore_eos 构造强制相等的
计数当精度门),引入开销(编译/捕获时间、额外显存、draft 成本、量化转换),
扣除开销后的净收益}。有损机制须补精度弥补证明(SPD:接受率+输出等价;
量化:精度分析+量化开销)。合成负载上语义精度不可评——内容哈希只证确定性
等价,有损臂另跑小规模真实 prompt 集。基线与优化臂同批重跑,不混用历史数字。

## 完整执行与自我迭代条款(强制,2026-09-21)

1. **严格执行完整 workflow 与 skill**:执行时必须加载 perf_trace_v3 的
   manifest(four_layer_pipeline.json)与全部 10 个 skill(含各自"本步坑位"
   节),按步全量执行、每步独立验收;**禁止自行简化、跳步、或以临时脚本
   绕过链驱动**(mm 链初期的临时化即反例,其代价已入目录)。
   归因方的每一轮迭代 = 走真实链步(profile 段 + S/M 链 + 验收),
   不是临场分析脚本。
2. **允许自我迭代成新版本,但升版须先征询用户**:途中发现 bug 或需求变化,
   可修复/修改——定义级修改即升版(v3 → v3.1 → …),升版前必须向用户提交
   提案{改什么、为何、影响哪些步}并获同意;同意后同步更新 manifest/skill/
   runtime,产生新指纹,留变更记录;禁止旧版本谱系上原地改语义。
3. **数据与产物复用规则(逐字)**:
   - 复用三条件,全部满足才可复用:①输入一致(workload 及全部输入文件
     sha256 相同);②该步产出已通过**独立验收**(不采信自报 gates);
     ③阶段定义未变(该步指纹与产出时一致,跨版本即指纹不同);
   - 任一条件不满足 → 该步产出不可用,该步及其**全部下游**重新运行;
   - 撤回/未验收产出移入 _stale,任何代码路径禁止读取;
   - 每次复用/重跑裁决写入账本(step、指纹、判据、决定),可审计。
