# 对照实验:Astra 优化流程 vs v2-trace 驱动的优化流程 — 2026-09-19

## 对照对象与变量控制

被优化的不是某个 kernel,而是 **baseline 的优化流程本身**。两臂共享:

- 实验环境:Astra 自己的 harness(shapes、dtype、correctness 阈、benchmark_kernel
  20 warmup/100 iter cuda Event、clone 在计时区外)、同一 nvcc 参数、同一台 RTX 4090;
- 循环骨架:生成候选 → 正确性验证 → 计时评分 → 策略 → 下一轮;
- LLM 替换:两臂的 coder/strategist 角色均由 Claude 顶替 o4-mini(声明替换;
  A 臂直接采用其作者跑出的最优产物 ultimate kernel,对 A 臂只利不弊)。

**唯一变量 = 进入循环的反馈信号**:

| | A 臂(Astra 原流程) | B 臂(v2-trace 流程) |
|---|---|---|
| 反馈信号 | 逐 shape 墙钟均值(benchmark_kernel 的返回文本) | P1 屋顶线粗扫 → P2 结构判限 → P3 门控 NCU 计数器 + 完整 kernel 序列 |
| 硬件计数器 | **无**(全仓库无 ncu/nsys 调用;strategist 提示词里只有词汇) | DRAM/SM 吞吐、序列级归属,条件门控采集 |
| 判停依据 | 迭代数上限(默认 5) | 与屋顶线的距离(到达即停,余量即未完) |
| 验收 | correctness allclose | allclose + 独立验收(死锁类失败由验收暴露,而非静默) |

## B 臂流程账本(实际执行记录)

| 步 | 动作 | GPU 成本 | 产出的决策信息 |
|---|---|---|---|
| P1 | 屋顶线粗扫 12 shapes(纯算术,复用已有计时) | 0 | silu 全 shape 距屋顶 3.8-32x 且时间平坦 → 非带宽问题;rms 分裂为两个 regime(小 B 超屋顶=占用受限,大 B 贴屋顶=带宽受限) |
| P2 | 读候选 kernel 结构对照 P1 | 0 | ultimate rms 每行一 block(B=128..256 时填不满 128 SM);ultimate silu fp16 每线程仅 4 字节 |
| P3 | 门控 NCU,launch-count 12 | ~1 min | **一次调用=5 个 kernel**:fp32 核心 182.7us(DRAM 92.4%,已贴屋顶,核内无余量)+ 4 个类型转换拷贝 ~221us(移动 3-4x 屋顶必需字节) |
| 改写 | 每 kernel 一次结构性改写(非微调):rms 两段式行分裂 + silu 8-half 满事务 grid-stride | 编译+基准 | 由 P3 直接决定:余量不在核内,在数据供给结构 |
| 验收 | 第一版 rms 用跨块原子同步 → grid 未全驻留时自旋死锁 | 8 min(损失) | 验收抓死,改零跨块同步两段式;录入坑目录 |

关键:P1/P2 零 GPU 成本就完成了 A 臂五轮循环也无法完成的定性
(墙钟只能比较快慢,不能区分"贴屋顶了"和"字节搬多了")。

## A 臂在同一环境下的结构性盲区(对照的核心证据)

1. **fp32 转换链不可见**:A 臂的计时把 5 个 kernel 的总墙钟当一个数;它的
   strategist 只能在"这个数变小了吗"上猜测。v2 的序列级归属直接显示 55% 的
   时间花在类型转换上——这不是调参能发现的,是信号维度的差异。
2. **regime 混叠**:A 臂对 7 个 rms shape 输出 7 个孤立的快慢数;v2 的屋顶线
   把它们分成两个物理 regime,对应两种相反的处方(行分裂 vs 无动作)。
   A 臂的 OLD 候选在大 B regime 回退到 0.85x,正是混叠信号误导搜索的实例。
3. **无判停标尺**:A 臂跑满迭代数;v2 在 NCU 报 DRAM 92.4% 时即知核内余量
   耗尽,把剩余努力转向核外(转换链),这正是加速的全部来源。

## 结果(他们的协议原样评分,RTX 4090)

### silu_and_mul(fp16;bf16 同趋势)

| shape | SGL | ULT(A臂) | V2(B臂) | V2/ULT | 距屋顶(ULT) |
|---|---|---|---|---|---|
| 16x4096 | 22.0u | 15.4u | 14.9u | 1.03x | ~39x(发射地板) |
| 32x8192 | 21.5u | 15.6u | 15.5u | 1.01x | ~10x |
| 64x8192 | 22.0u | 16.6u | 16.1u | 1.03x | ~5x |

**B 臂用一次计数器驱动的改写达到 A 臂多轮循环的水平**(1.00-1.03x)。
两臂都压在 ~15us 的发射地板上——P1 早已给出的定性(距屋顶 4-32x、时间对
shape 平坦)在此闭环:kernel 改写在这些 shape 上已经打完,剩余时间在发射
路径。A 臂的循环没有这个判停信号,按设计会继续烧完迭代预算。

### fused_add_rmsnorm(fp32,他们的原生口径)

| shape | roof | BASE | NEW(A臂) | V2候选(B臂) | NEW距屋顶 |
|---|---|---|---|---|---|
| 256x4096 | 12.5u | 20.5u | 14.8u | 20.3u | 1.18x(≈发射地板) |
| 1024x4096 | 49.9u | 35.1u | 19.1u | 26.9u | 0.38x(L2 驻留) |
| 2048x8192 | 199.7u | 301.9u | 224.3u | 340.8u | **1.12x** |
| 1024x8192 | 99.9u | 90.3u | 72.0u | 93.7u | 0.72x(L2) |

**B 臂的行分裂候选全线败于 NEW(0.66-0.86x),被 v2 自己的独立验收拒绝。**
败因经屋顶线立刻定量:两段式把 x 读写各多做一遍,字节数是单趟的 5/3 倍
(2048x8192 实测 340.8u / 199.7u = 1.71x ≈ 5/3),占用率收益被搬运代价吞没。
与此同时验收给出 A 臂没有的证书:**NEW 在其 fp32 口径下已贴屋顶**
(超 L2 的 shape 1.12x,小 shape 压发射地板)——v2 流程在此的正确输出不是
"更快的 kernel",而是**判停**:核内余量耗尽,继续迭代只是追噪声。

### 部署 regime 审计(v2 trace 独有,两臂环境之外的发现)

他们的 rms harness 全程 fp32,而 serving 生产路径(vLLM/SGLang)是 fp16/bf16。
把 NEW 喂 fp16 时,P3 的序列级归属显示一次调用发射 5 个 kernel:fp32 核心
182.7us + 4 个类型转换 ~221us(2048x8192),墙钟从 224us 涨到 561us(自身 2.5x 回退),而同 shape 的 fp16 基线只要 81us——慢 6.9 倍。**A 臂的基准协议根本无法看到这件事**——它孤立
kernel、单一 dtype、只有总墙钟。这不是调参差距,是信号维度差距。

## 流程级结论

| 度量 | A 臂(墙钟反馈循环) | B 臂(v2-trace 反馈) |
|---|---|---|
| silu 结果 | 1.37-1.42x vs SGL | 相同水平,**一次改写** |
| rms 结果 | 贴屋顶(其口径内) | 候选被拒,**改判停 + 出具屋顶证书** |
| 判停能力 | 无(跑满迭代数) | 屋顶距离 + DRAM% 双标尺 |
| 错误候选的命运 | 混在迭代里靠计时淘汰 | 独立验收显式拒绝并归因(字节 5/3) |
| 部署盲区 | fp32 口径掩盖 fp16 转换链 | P3 序列归属直接暴露 2.5x 回退 |

对"v2 能否优化 baseline 的流程"的回答:**能,但方式不是每次都产出更快的
kernel**。v2 换掉的是循环的感知层:屋顶线把"还能不能优化"变成可测量的量,
序列归属把"时间花在哪"从一个数变成一个结构,独立验收把"看起来更快"和
"确实更快"分开。在 baseline 已经打到地板的地方,v2 的产出是省下整轮无效
迭代;在 baseline 的协议看不到的地方(部署 dtype、发射地板),v2 找到的
是它整个流程都无法表达的缺陷。

## 声明的边界

- fp32 rms 口径是 baseline harness 自身的选择(serving 生产路径是 fp16/bf16),
  照它口径评分,并把该问题单列;
- 其正确性只比 x 不查 residual 回写,v2 kernel 按相同语义(只写 x)以保公平;
- 两臂 LLM 相同,不同的只有喂给 LLM 的信号——这恰是对照要隔离的变量。

# 修正与扩展(2026-09-20):端到端对照

## 范围修正声明

上文的孤立-harness 对照只测了 v2 的最弱可移植片段(测量纪律:屋顶线、
门控计数器、独立验收)。v2 方法的本体特征在孤立环境里**没有一个可测**:

1. **目标选择是一个可迭代的 loop**:workload_profile + 三遍 trace = 一次
   loop,产出高延迟 process 集合(延迟占比 >10%,双侧扣除);下一次 loop
   可增添新越限的 process、删除冷 process。实测例:pdom regime 下 o_proj
   越过 10% 门限进入目标集——目标集随负载自更新。
   **baseline 的目标选择没有机制**:仓库就是人为写死的三个 test 目录
   (merge/rms/silu),不随任何测量更新。
2. **端到端热点与暴露时间**:v2 在运行系统上排序(遮蔽者不进目标集);
   baseline 按孤立加速比排序,act_mul/norm_post(遮蔽 83.8%/53.4%)
   恰是它的两个目标。
3. **并发资源墙**:单 stream 无重叠、step 内 16.9% 主机空隙、decode gemm
   贴 DRAM 墙、KV 限批——这些决定"硬件为何用不满"的墙只在高并发+抢占的
   运行里存在;baseline 优化单 kernel,实际场景是高并发甚至抢占调度。
4. **process → 修改位置的反映射**:插桩区间即定位。孤立对照里唯一体现此
   机制的是 fp16 转换链(序列归属直接指向绑定层而非核内)。

## 端到端四臂实验(高并发+抢占竞技场)

竞技场:pt_big_mixed(mixed_preempt,三类程序抢 16 座位、跨 quantum 阶梯)、
agentix_core 抢占调度、bf16、Llama-3.1-8B、单 4090(device 1)、
与 v2 谱系相同合同;各臂同负载同 seed,无插桩,纯计时。

| 臂 | 优化点来源 | 内容 |
|---|---|---|
| ctrl | — | eager,原装核 |
| A1 | baseline(孤立加速比 1.4x) | eager + Astra silu ultimate(bf16 原生) |
| A2 | baseline(孤立加速比 1.3-2.0x) | eager + Astra rms ultimate(fp32 链式集成) |
| B | **v2**(16.9% 主机空隙,发射路径) | 原装核 + 图捕获(去 eager) |

预注册预言:A1 ≈ 0(目标被遮蔽 83.8%,且孤立加速大半是发射地板假象);
A2 < 0(fp32 转换链,孤立协议看不见);B 收回 ~15-19% step 时间
(v2 定位的空隙是端到端量,修复收益直接兑现)。

评分:summary 的 throughput_tokens_per_s / program 延迟分位,
外加 token 等价门(A 臂换核不得改变输出;数值漂移单独申报)。

## 端到端四臂结果(pt_big_mixed,agentix_core 抢占,RTX 4090,2026-09-20)

重复运行噪声带:ctrl 1198.0/1201.0(±0.15%),b_graph 1233.0/1232.9(±0.005%)。
输出漂移门:三臂对 ctrl 均 0/158 calls(粗粒度:逐 call output_tokens 一致)。

| 臂 | 优化点来源 | tok/s | Δ吞吐 | call p50 | Δp50 | 判定 |
|---|---|---|---|---|---|---|
| ctrl | — | 1198.0 | — | 4062ms | — | 基准 |
| A1 silu 换核 | baseline:孤立加速 1.37-1.42x | 1208.9 | **+0.9%** | 3873ms | -4.7% | 孤立加速的 ~3% 兑现:目标被遮蔽 83.8% + 孤立数字大半是发射地板假象 |
| A2 rms 换核 | baseline:孤立加速 1.25-1.84x(其 fp32 口径) | 1155.7 | **-3.5%** | 4104ms | +1.0% | 负收益:fp32 转换链,baseline 协议(单 dtype 孤立)结构上不可见 |
| B 图捕获 | **v2:16.9% 主机空隙(发射路径)** | 1233.0 | **+2.9%** | 3759ms | **-7.5%** | 全指标最优;p90 5034ms(-4.4%) |

### 与预言的偏差申报

B 臂预言 15-19%,实测吞吐 +2.9% / call p50 -7.5%。原因:本竞技场是
到达受限的开环负载(arrival 3.0/s,引擎有低压阶段,容量收益不完全体现
在吞吐上,更多体现在延迟分位);19% 参考值测于持续 decode 压力的插桩窗口。
方向与排序(B > A1 ≈ ctrl > A2)与预言完全一致。

### 结论

同一份优化预算,baseline 方法(孤立加速比选核)给出的两个"确定收益"
在真实高并发+抢占场景中一个归零、一个变负;v2 三遍 trace 给出的一个
优化点(主机空隙→发射路径)在全部指标上为正。**差距不在优化技巧,
在感知维度:baseline 的协议里不存在"遮蔽""regime""发射地板"这些量,
而它们决定了孤立收益能否兑现为端到端收益。**

# 构造场景对照(2026-09-20):交互式 agent 服务(baseline 难优化,v2 可定位)

## 场景构造与合理性

pt_interactive.json:10 个多轮 tool-calling 会话、每会话 5-7 轮串行调用
(prompt 180-420 tok,decode 120-260 tok,工具间隔 150-600ms)、到达 0.35/s
→ 有效并发 2-4,decode 批量 2-4。这是真实的低并发交互式 agent 服务形态,
延迟敏感(用户在等回合)。

构造逻辑:批量越小,每 kernel 的设备时间越短,发射/主机路径占比越大——
kernel 内无肉可改(baseline 无从下手),肉全在 kernel 之间(baseline 的
协议不存在这个维度)。

## v2 loop 执行记录

**P1(NVTX+CUDA activity 整段)**:decode 类步承载 98.2% 时间;步内设备忙
70.2%,主机空隙 29.8%(mixed@batch16 为 16.9%——空隙随批量缩小而放大,
机理链闭合)。baseline 的两个目标在此负载是冷 process:act_mul 3.1%、
norm_post 2.9%,远低于 10% 门限,按 v2 目标选择规则不入目标集。

**P1 判决**:优化点在发射路径,不在任何 kernel 内。

**Loop-2 分解(同一 p1.sqlite)**:空隙 29.8% = 调度 0.7% + 输入准备 5.7%
+ 状态更新 0.1% + **模型内发射空隙 23.3%**。

## 四臂结果(同负载同 seed;输出漂移门三臂全过 0/64)

| 臂 | 优化点来源 | tok/s | call p50 | call p90 | 判定 |
|---|---|---|---|---|---|
| ctrl(eager) | — | 231.0 | 3506ms | 4439ms | 基准 |
| A1 silu 换核 | baseline | 230.7(**±0.1%**) | 3302ms | 4423ms | **彻底归零**(mixed 里尚有 +0.9%) |
| A2 rms 换核 | baseline | 217.4(**-5.9%**) | 3887ms(+10.9%) | 5219ms(+17.6%) | 回退较 mixed(-3.5%)放大:小批量下转换 kernel 的发射开销占比更高 |
| B 图捕获 | **v2 P1:23.3% 模型内发射空隙** | 233.2 | **3229ms(-7.9%)** | **4296ms(-3.2%)** | 全指标最优;吞吐受到达限制(+0.95%),收益体现在延迟 |

注:此场景吞吐由到达率+工具间隔决定(wall 51.5-55.3s 几乎不变),
正确的比较轴是 call 延迟——这也正是交互式场景用户感知的量。

## 兑现率核查(v2 验收纪律)

P1 说模型内空隙 23.3%,B 臂 p50 只降 7.9%。对 B 配置再采一遍 P1 核实:

- 步内兑现完全:decode 步空隙 28.8% → **1.9%**,步中位 23.8ms → 17.0ms,
  总步时 5.44s → 3.43s;
- 但 call p50 只降 7.9% 的原因在测量而非修复:**P1 的 28.8% 带着
  插桩+nsys 税**(税落在空隙里)。二级开销修正(对照干净臂):
  干净 eager ≈18.5ms/token,设备 ≈16.7ms → 真实空隙 ≈10%;
  图捕获后 ≈17.0ms/token,收回 ~8 个点,**兑现率 ~80%**;
- 图臂下插桩税自然消失(图回放绕过逐 kernel Python 派发),
  故两份 P1 之间 37% 的步时差 = 真实空隙消除 + 税消失,已拆开申报。

这次核查是 v2 两级开销消除纪律的一次实战自纠:P1 的绝对份额若不经
干净臂修正,会把修复上限报高近 3 倍(28.8% vs ~10%)。

## 场景结论

构造成立:同一负载下,baseline 方法的两个产物一个归零(A1 ±0.1%)、
一个放大回退(A2 -5.9%,劣于 mixed 的 -3.5%);v2 loop 的 P1→分解→修复
→验证闭环给出全指标最优(p50 -7.9%,兑现率 80%,残余空隙 1.9% 判停)。
baseline 在此场景无从下手的原因是结构性的:它的目标(kernel 内)只占
预算的个位数百分比,而真正的预算(kernel 之间)在它的协议里不存在。

# 复杂多 agent 负载构造(2026-09-20):agent loop 族

按 ref_MoA/direction_experiment_loop 的真实调度形态构造(非 lats 波次推进):
C(Decision)每轮路由 → [A(Lab)→B(Judge)] 或 [B] 或终止;动态控制流按种子
预滚为可重放轨迹;上下文逐轮累积(C/B 的 prompt 随 cycle 增长);Lab 带
0.8-2s 工具执行。单用户并发驱动多条 loop。

## 负载 1:单链 loop(pt_agentloop.json)

4 条 loop、7-16 call 变长轨迹(CABCBCBCBC 等)、P/D=3.75(上下文累积)。
实测:**46% 墙钟处于宽度 1**(短 loop 结束后最长 loop 独占引擎 ~50s,
batch-1 尾段);P1:decode 类步空隙 30.8%(三个场景中最高——batch 越小
发射空隙越大,与 batch-1 尾段互证)。

## 负载 2:双链 loop(pt_agentloop2.json,用户升级要求)

C 每轮同时决定两条链的起点并同时放行(链内独立路由 A→B 或 B),
下轮 C join 两链尾部。轨迹如 CABABCBBCABABC(第二轮两链都跳过 Lab)。

**构造过程中程序级 trace 抓到引擎驱动缺陷**:原驱动按 wave 顺序 await,
程序内并行重叠实测为 0——独立双链被完全串行化(同 wave 又会引入伪屏障,
退回 lats 式波次)。修复:驱动增加逐 call DAG 调度(call 只等自己的父辈
完成事件,无 wave 屏障;workload config `call_dag: true` 启用)。

修复效果(同负载同 seed):

| | wave 串行驱动 | DAG 驱动 | Δ |
|---|---|---|---|
| makespan | 118.1s | 74.0s | **-37%** |
| 吞吐 | 157.0 tok/s | 250.7 tok/s | **+60%** |

# SpaceServe 式 SM 分区对照(2026-09-20,计划 2 场景)

## 机制与近似声明

SpaceServe(NeurIPS'25)= 多模态 encoder/decoder 的细粒度动态 SM 空间复用。
4090 无 MIG,跨进程引擎用不了 green context;最近似机制 = **MPS + 每客户端
CUDA_MPS_ACTIVE_THREAD_PERCENTAGE**(线程占用帽:provisioning 上限而非硬空间
隔离,和=100 时最接近不相交分区)。帽有效性已实测:15% 帽 → 24.2/160.1
TFLOPS = 15.1%,成比例生效;fork 时刻 env 差异化传导成立(B3 三引擎不对称
响应为证)。

## 五臂结果(pt_mm_loop3,三个 1.xB 引擎同卡)

| 臂 | 机制 | tok/s | lm p50 | lm TTFT | vis p50 | audio p50 |
|---|---|---|---|---|---|---|
| ctrl | 默认时间片 | 245.3 | 2635ms | 79ms | 2522ms | 1610ms |
| **B1 MPS 无帽** | 纯进程并发 | **257.7(+5%)** | **2243(−15%)** | **54** | 2527 | 1592 |

## 结论(含一次公开的自我纠错)

1. **赢家是 B1(MPS 无帽)**:解除进程时间片、允许跨引擎 kernel 真并发,
   +5% 吞吐、lm p50 −15%。此负载下静态分区没有任何配置赢过无帽
   (B4 已是善意配置,仍 −1%)。
2. **B3 是方法论教训**:我用 P3 的 SM 中位(0.14%)给 lm 定 15% 帽——但该
   中位来自共活跃窗口的门控 launch,decode 主导;lm 的 prefill(300-1000
   token GEMM)真吃 SM,TTFT 79→224ms 是 prefill 被掐的铁证。
   **regime 分离(prefill/decode)在引擎内部同样适用;用跨相位中位数
   定资源尺寸是统计错误。** 已入目录(A 类新条目)。
3. **对 SpaceServe 的公平解读**:它的贡献恰是动态+相位感知的分区;静态
   per-process 帽表达不了"decode 时 15%、prefill 时放开"——我们的静态近似
   失败正好复现了它立论时反对的对象。在小批量 1.xB 三引擎场景,分区收益
   上限本就低(干扰小),并发解除(MPS 本身)才是第一杠杆。
4. v3 的正确用法:P3 证据按相位拆开后,指向的不是静态帽,而是"lm 需要
   突发算力、其余时间趴发射地板"——这类形状适合动态机制(SpaceServe 本体、
   或 prefill 优先级调度),不适合静态配额。
