G05 · 模板 → 目标预测

选择性分析与资源缺口

G06–G10 · 选择 = decode_layer*

10% 阈值选择（层卷积后）在三个工作流上一致命中 decode_layer*。资源窗口把 w03 家族指标挂到选中 process：gemv 的 74% DRAM active 是唯一的硬件墙；上界分析给出 gpu_idle_window ≈ 80.5–81.9% wall——若 host 派发被完全隐藏或消除的收益上限。

优化杠杆（按收益上界）

react_moa_mcts；native 链的杠杆（输入生成搬上 GPU）在本链收益 ≈ 0

隐藏/消除 host 派发（CUDA graphs · compile · 融合）80.5% 提高 decode 权重带宽利用（量化 · 更大 batch）~11.9% 输入生成搬上 GPU（native 链主杠杆）≈0%

第二行 = gemv 占 wall 的份额（61% GPU 时间 × 19.6% GPU busy）；量化把每字节权重换成更多 token，是带宽墙内的收益。

Agentix 8B 复现：LLaMA-3.1-8B 上的 serving 链

vLLM 0.29 · w01'–w05''

论文（NSDI'26 Agentix/Autellix）在 8×A100 的改版 vLLM v0.6.1 上做程序级调度；本复现在同一张 4090 上用原版 vLLM 0.29 承载重实现的 PLAS/ATLAS，负载按论文 Fig.11 统计量校准（sharegpt/bfcl/lats + Mixed，Poisson 到达，LATS 多线程 wave）。AutoTrace 以 serving 适配链（w01'–w05''）应用于此实验。完整报告：experiments/h23-agentix-8b/{results,AUDIT}.md。

排队区间：FCFS vs PLAS（统一 max batch=16）

program-level token latency，越短越好；论文协议允许统一 batch 上限（§6.2）

FCFS · mean28.5 ms PLAS · mean20.6 ms FCFS · p9058.0 ms PLAS · p9033.3 ms FCFS · bfcl 类（短程序）56.7 ms PLAS · bfcl 类30.3 ms

短程序收益最大、长程序（lats 11.0→12.6 ms）小幅付出——正是 PLAS「已得服务少者优先」的语义。到达率扫描 0.1–0.8 prog/s（无 batch 上限）三策略完全重合：单卡 + 60 s 到达窗下引擎不排队（峰值 in-flight 60<64），无队列则程序级调度无杠杆——论文的 4–15× 需要其测试台的持续过载稳态；与本对照可比的端点是 Agentix ≈2×（对 vLLM-opt）。

墙的迁移：eager 单请求（h22）vs 连续批处理 serving（h23）

NCU 中位数，占各单元峰值百分比；同一张 4090

h22 decode gemv · DRAM active75% h23 serving gemm · DRAM active18% h22 decode gemv · L247% h23 serving gemm · L276% h22 decode gemv · Tensor pipe0% h23 serving gemm · Tensor pipe49%

连续批处理把 decode 从 gemv/DRAM 墙搬到 GEMM 的 L2/张量流水墙——h22 的「decode gemv 占 62% GPU 时间、DRAM 74%」是单请求现象，在 serving 引擎下 gemv 仅占 3–8%。这是三条模型链合并后的核心系统结论。
